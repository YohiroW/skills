# 研究文章与引用规范

## 写作组织

根据问题选择章节，不要求固定字数或凑齐模板。默认中文，围绕技术问题连续展开，避免写成资料目录或逐篇摘要。通常需要覆盖：

1. **问题与主要发现**：到底要解决什么问题，关键结论与适用范围是什么。交代检索截止日期、平台或版本等重要假设。
2. **机制与路线**：必要背景、数据表示、执行过程和系统集成；相近方法的共同点与关键差异。
3. **项目实践**：将游戏、团队、演讲年份与具体做法关联，解释项目约束为何促成该设计。缺乏生产案例时明确说明。
4. **比较与取舍**：在可比条件下讨论成本、收益、质量、内容制作和维护影响。表格适合并列比较，正文承担因果解释。
5. **选型与待验证问题**：建议绑定条件；如用户未提供项目预算，用条件式建议，不能直接宣布唯一最佳方案。指出本地实验可以验证什么，不冒充已做实验。
6. **来源与研究边界**：列出直接引用的资料；简述检索过的关键来源族、访问缺口、时间限制和未解决的分歧。未读候选可单独列为延伸阅读，不混入支撑结论的证据。

适度使用示意图或说明性伪代码解释复杂机制，图和代码都要服务于研究问题。不要把概念示意包装成生产实现。

## 引用与证据定位

采用稳定的 `[S1]`、`[S2]` 编号或等效 Markdown 引用格式，紧跟所支持的论断。机制、采用情况、数据与历史归属均应能追溯，避免整章末尾只有一个笼统链接。

正文示例格式：

> 团队使用某种更新策略降低重复计算；该描述针对演讲中的特定场景。[S1，幻灯片 18–22]
>
> 据此可以推测，它对大量快速变化对象的收益可能不同。这是本文推断，原资料未给出该场景测试。

示例中的页码仅演示格式，实际使用必须来自已核验资料。区分 PDF 文件页码与幻灯片编号；缺少分页时用真实章节标题。视频使用实际核验的时间戳，字幕只能支持其覆盖的内容，不足以推断未见的图表。网页无稳定定位时引用小节名称及短小必要引文，不编造定位。

来源条目建议格式：

```text
[S1] 作者 / 团队：《原始标题》，会议或发布机构，发表年份。
     类型：讲稿 / 录像 / 论文 / 官方实现 / 技术文章。
     链接：具体材料的公开 URL；必要时附项目页或公开替代版本。
     使用位置：页码 / 章节 / 视频时间戳。
     访问情况：实际读取的材料与访问日期；必要的访问限制。
```

不明确的作者、年份或版本写“未标明”，不要从 URL 或上下文猜测后当成事实。引用代码时尽量固定到版本、标签或提交；这类来源证明的是该版本的行为。

## 定量信息与比较

性能表中按需保留：工作负载、平台/GPU、分辨率、质量、时间/内存、测量范围、来源定位和未知条件。只有原资料支持时才填数值；无数据时写“未报告”，不估填。对于不同比较条件，分别陈述结果并明确不可直接排名。

把“论文报告的测试结果”“开发者对项目的陈述”和“本文的解释”在措辞上分开。厂商宣传中的收益数字须保留测试前提，缺失前提会限制可得出的结论。

## 交付前的内容检查

- 开头能直接回答研究问题，主体解释为何成立，结论没有超出证据范围。
- 读者能够顺着引用找到支持核心结论的具体材料；付费页面的简介未被当成完整技术依据。
- 项目名称、术语、时间线和版本在全文一致；一篇论文及其转载未被当成多份独立验证。
- 未检索到证据表述为“本次检索未找到”，而非“没有项目这样做”。
- 重要访问缺口写在文章中，不能只在聊天回复中披露。
